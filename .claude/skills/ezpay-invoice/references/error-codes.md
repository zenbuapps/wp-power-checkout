# ezPay 電子發票 錯誤代碼

對應 EZP_INVI_1.2.1 第九章「錯誤代碼」。所有 API 失敗時，回應的 `Status` 欄位
（成功為 `SUCCESS`）會帶下列錯誤代碼之一。錯誤代碼分五個前綴系列：

| 前綴 | 系列 |
|------|------|
| `KEY` | 金鑰 / 傳輸 / 解密相關 |
| `INV` | 發票業務邏輯相關 |
| `LIB` | 自訂編號 / 作廢相關 |
| `IAI` | 作廢折讓相關 |
| `NOR` | 網路相關 |

> **本表只適用開立 / 作廢 / 折讓 / 查詢這 7 支 API。** 字軌管理 API 的錯誤碼見
> `track-management.md`，手機條碼 / 捐贈碼驗證 API 的見 `carrier-validation.md`。
> 三份手冊有**同碼不同義**的情況（例：`LIB10007` 在這裡是「已開折讓無法作廢」，
> 在字軌管理是「資料已存在」）——錯誤處理必須以「API + 錯誤碼」判斷，不能只看錯誤碼。

## 完整錯誤碼表

| 錯誤代碼 | 錯誤原因 | 備註 |
|----------|----------|------|
| `KEY10002` | 資料解密錯誤 | `PostData_` AES 解密失敗（HashKey/IV 錯、padding 錯、加密模式錯）|
| `KEY10004` | 資料不齊全 | |
| `KEY10006` | 商店未申請啟用電子發票 | 需先在平台申請並通過審核 |
| `KEY10007` | 頁面停留超過 30 分鐘 | |
| `KEY10010` | 商店代號空白 | `MerchantID_` 未帶或為空 |
| `KEY10011` | PostData_ 欄位空白 | `PostData_` 未帶或為空 |
| `KEY10012` | 資料傳遞錯誤 | |
| `KEY10013` | 資料空白 | |
| `KEY10014` | TimeOut | |
| `KEY10015` | 發票金額格式錯誤 | |
| `INV10003` | 商品資訊格式錯誤或缺少資料 | `ItemName` / `ItemCount` / `ItemUnit` / `ItemPrice` / `ItemAmt` 等格式或數量不一致 |
| `INV10004` | 商品資訊的商品小計計算錯誤 | `ItemAmt ≠ ItemCount × ItemPrice` |
| `INV10006` | 稅率格式錯誤 | `TaxRate` 格式錯誤 |
| `INV10012` | 發票金額、課稅別驗證錯誤 | `TotalAmt ≠ Amt + TaxAmt`，或課稅別與金額不一致 |
| `INV10013` | 發票欄位資料不齊全或格式錯誤 | 沙箱實測：`Message` 會指出欄位，例「欄位資料格式錯誤-TimeStamp」「欄位資料格式錯誤-Version」（`Version` 填錯回這個）|

| `INV10019` | 資料含有控制碼 | 欄位含不合法控制字元 |

| `INV90005` | 未簽定合約或合約已到期 | 沙箱實測 `Message`：「期間內無可用合約」。**新申請的測試商店也會回這個**：平台沒有自助申請合約的入口，要請 ezPay 客服（cs@ezpay.com.tw）開通測試合約。合約狀態可在平台【發票管理 › 管理設定 › 使用狀況】查看，該頁空白就代表沒有合約。格式檢核在合約檢核之前，所以格式錯誤的請求會先回 `INV10003` / `INV10004` / `INV10012` / `INV10013` |

## 依 API 分類的常見錯誤

| API | 常見錯誤碼 |
|-----|-----------|
| 開立發票 `invoice_issue` | `KEY10002`（解密）、`INV10003`（商品格式）、`INV10004`（小計計算）、`INV10012`（金額驗證）、`INV10013`（欄位不齊）、`INV10014`（自訂編號格式）、`INV10017`（版本不支援混合稅率）、`INV90006`（張數用罄）、`LIB10003`（自訂編號重覆）|
| 觸發開立發票 `invoice_touch_issue` | `KEY10002`、`KEY10004`、`INV10013` |
| 作廢發票 `invoice_invalid` | `INV20006`（查無發票）、`INV70002`（上傳失敗不得作廢）、`LIB10005`（已作廢過）、`LIB10007`（已開折讓無法作廢）、`LIB10008`（超過作廢期限）、`LIB10009`（未上傳財政部無法作廢）|
| 開立折讓 `allowance_issue` | `KEY10002`、`INV10003`、`INV10004`、`INV20006`、`INV10013` |
| 觸發確認/取消折讓 `allowance_touch_issue` | `KEY10002`、`INV10013` |
| 作廢折讓 `allowanceInvalid` | `IAI10001`~`IAI10006` |
| 查詢發票 `invoice_search` | `KEY10002`、`INV20006`（查無發票）|

## 沙箱實測：商店沒有合約時各 API 的回應（2026-09-29）

用不存在的發票號碼 / 折讓號探測，確認加密、欄位、Version 都被平台接受到哪一關：

| API | 回應 | 說明 |
|-----|------|------|
| `invoice_issue` | 格式錯 → `INV10003` / `INV10004` / `INV10012` / `INV10013`；格式對 → `INV90005` | 格式檢核在合約檢核之前 |
| `invoice_touch_issue` | `INV90005` | 被合約擋住 |
| `invoice_search`（兩種 SearchType）| `INV20006`「查無發票資料」| 不需合約；缺查詢鍵回 `INV10013`「欄位資料空白-InvoiceNumber」|
| `invoice_invalid` | `INV20006`「查無發票資料」| 不需合約 |
| `allowance_issue` | `INV20006`「查無發票資料」| 不需合約；**先查發票是否存在、後檢核金額**——小計算錯也是回 `INV20006` |
| `allowance_touch_issue` | `INV20006`「查無折讓單資料」| 不需合約 |
| `allowanceInvalid` | `IAI10002`「查詢失敗-查無折讓單資料」| 不需合約 |
| `checkBarCode` / `checkLoveCode` | `SUCCESS` | 不需合約（見 carrier-validation.md）|

## 錯誤處理建議

| 錯誤類別 | 處置 |
|----------|------|
| `KEY10002` 解密錯誤 | 多半是 AES padding / HashKey / HashIV 設定問題——檢查加密實作（見 concepts.md），**不要重試** |
| `KEY10010` / `KEY10011` / `KEY10013` 資料空白 | 程式組裝 body 的 bug，修正後再送 |
| `INV10003` / `INV10004` / `INV10012` 金額 / 商品計算錯誤 | 後端金額計算邏輯有誤，修正後再送（見 api-reference.md「金額計算」）|
| `LIB10003` 自訂編號重覆 | **先別換編號重開**——多半是前一次請求其實成功了。用 `invoice_search`（`SearchType=1`，`MerchantOrderNo` + `TotalAmt`）取回原發票；查到就視為已開立，查不到才人工處理（見 concepts.md「重送與冪等」）|
| `INV90006` 張數用罄 | 暫停開立並通知管理員；可用字軌管理 API 查詢 / 新增字軌（見 track-management.md）|
| `LIB10008` / `LIB10007` / `INV70002` 作廢限制 | 不可作廢的業務狀態——改走開折讓（`allowance_issue`）或人工處理 |
| `LIB10009` 未上傳財政部 | 暫時性：隔日 06:00 上傳結果更新後再試作廢；不要立刻改走折讓 |
| `NOR10001` / `KEY10014` 網路 / TimeOut | 短暫性錯誤——可重試，但必須重送**存下來的同一份 `PostData_` 字串**；重新組參數會因 `TimeStamp` 改變而撞 `LIB10003` |

## 作廢的冪等判斷

同一張發票的作廢請求可能被重複觸發（自動作廢 + 手動作廢、或重送）：

| 回應 | 處置 |
|------|------|
| `SUCCESS` | 作廢成功 |
| `LIB10005`（已作廢過）| 視為作廢成功（目標狀態已達成）|
| `INV20006`（查無發票）| **不要**直接視為成功——先用 `invoice_search` 確認發票號碼與商店是否正確；確認平台上確實不存在，才清除本地紀錄 |
