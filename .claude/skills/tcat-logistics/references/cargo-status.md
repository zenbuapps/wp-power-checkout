# 貨態查詢：三條路徑 + 兩套代碼系統

黑貓提供三種取得貨態的方式，**分別使用不同的代碼系統**。這是整合時最容易出錯的地方。

## 1. 三條路徑對照

| # | 路徑 | 適用情境 | 即時性 | 批次量 | 代碼系統 | 需要的憑證 |
|---|---|---|---|---|---|---|
| 1 | **官網貨態查詢 URL** | 單筆、人工查詢 / 客服 | 即時 | 1 筆 | 無代碼（只有顯示文字）| 無 / 契客帳密 |
| 2 | **`OBTStatus` API** | 系統即時查詢、使用者按「查詢物流」 | 即時 | **≤ 10 筆單號** | **二代**（3 碼，如 `111`/`301`）| `CustomerId` + `CustomerToken` |
| 3 | **FTP `.sod` 回檔** | 全量定期更新資料庫 | **每日 05:00 / 18:00** | 全量 | **一代**（5 碼，如 `00001`/`00003`）| FTP 帳號密碼 + IP 白名單 |

**建議架構**：以 **FTP `.sod` 批次**為主力來源（全量、免打 API），以 **`OBTStatus`** 為使用者主動查詢時的即時補強。兩者寫入同一張貨態表前，**必須先正規化成統一狀態機**（見 §5）。

## 2. 路徑 1：官網貨態查詢 URL

| 情境 | URL |
|---|---|
| 系統裡有單號 | `http://www.t-cat.com.tw/Inquire/TraceDetail.aspx?BillID={單號}` |
| 系統裡只有訂單編號 | `https://www.takkyubin.com.tw/ymtcontract/Status/Check.aspx?CustID={客戶代號}&CustPW={契客密碼}&OrderID={訂單編號}` |

> ⚠️ **第二個 URL 會把契客密碼放在 query string**。不要在伺服器端組這個 URL 後轉址給終端使用者（密碼會出現在瀏覽器歷史、Referer header、CDN / proxy log）。僅適合內部客服人員手動使用。對外請一律走 `OBTStatus` API。

> 「狀態定義」三欄是**建議的後續處理動作**：`訂單取消` → 該筆逆物流作廢；`隔日再配` → 系統不需動作，等下次；`廠商聯繫` → 需人工介入補正資料或聯絡客戶。

## 8. 整合檢核清單

- [ ] `OBTStatus` 查無貨態時回 `IsOK=N` + `Data=null`，**不是錯誤**，不要告警。
- [ ] `OBTStatus` 一次最多 10 筆，且**只回有貨態的單號**——要自行對位補「無貨態」。
- [ ] `OBTStatus` 的 `StatusList` **由新到舊排序**，`[0]` 即最新（與外層 `StatusId` 一致）。
- [ ] 代碼世代要在入庫時標記（`code_generation: 'v1' | 'v2'`），不可混存同一欄位而不註記。
- [ ] 一代代碼保留前導零，以字串處理，並 `trim()`（`216　` 帶全形空白）。
- [ ] 未知代碼走 `UNKNOWN` 並保留原值，**不可 throw**。
- [ ] `00399` / `305`（退貨配完）語意特殊：**曾經退貨的包裹，其「配完」會被改寫成退貨配完**，不要當成正常送達。
- [ ] `.sod` 每日只有 05:00 / 18:00 兩批，**不要期待即時**；需要即時請走 `OBTStatus`。
